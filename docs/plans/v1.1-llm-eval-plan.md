# V1.1 LLM 测评计划（分阶段）

目标：对当前 v1_llm 基准（`benchmarks/v1_llm/questions/`，1000 题，profile v1.1，3 选项）完成 LLM 测评。不一步到位，先小规模验证再全量。

## 背景与参照

- 旧版题库（`benchmarks/v1_llm_legacy/`）已完成 13 个模型的全量测评，成绩区间 41.6%–72.6%（随机基线 33.3%）。本计划选用的模型优先来自该名单，以便新旧题库成绩可逐模型对比。
- 注意：旧版与 v1.1 题目不同（v1.1 移除 KAN、简化 profile），绝对分数不可直接比较，仅模型相对排序有参考价值。
- 中转站 gpt.ge（OpenAI 兼容协议）提供全部候选模型，单一 key 即可跑全部。

## 题库构成（抽样依据）

| 维度 | 分布 |

## 分阶段执行

### Stage 0 — 冒烟（5 模型 × 10 题）

- 目的：验证中转站连通性、model 名称、`<answer>` 解析率、token 上限是否截断。
- 除了看结果是否返回，还要逐模型审查：API 是否正常返回、响应是否成功写入逐题结果文件、`run.json` 是否完整记录模型配置和统计、是否存在错误/截断/未解析答案、原始回复和 prompt 是否留存。通过后才进入 Stage 1；失败则调整 model 名 / `OPENAI_MAX_TOKENS_PARAM` / `--max-tokens` 或并发数。

### Stage 1 — 轻量测评（5 模型 × 300 题）

- 抽样：方案 A 分层抽样。按 family × dataset bucket × 题型分层；`synthetic_tabular_classification` 的 `general_tabular`、`spiral`、`xor` 三类也分别按原比例抽取，再按各层比例抽取题型。固定 seed，生成 symlink 子集目录（loader 原生支持，不改评测代码）。
- 统计效力：n=300，95% CI ≈ ±5.5%。只看档次差距，不做精细排名。
- 产出：5 个 `llm_runs/` 运行 + 对比表（`tools/llm_eval/compare_eval_runs.py`）。

### 决策点

Stage 1 后确认：档位排序是否与旧版一致；是否替换个别模型（如某档两模型拉不开差距）；再进全量。

### Stage 2 — 全量测评（约 10–15 个模型 × 1000 题）

- Stage 1 后最终确认并扩充模型名单，目标约十几个模型，覆盖前沿闭源、国产/开源、推理/非推理及不同价格档位。
- 对已经完成 Stage 1 的模型，用 `--skip-existing` 复用 300 题结果，每模型只需补 700 题；新增模型直接跑 1000 题。
- 统计效力：n=1000，95% CI ≈ ±3%。
- 产出：最终对比报告（总体 + 按 family、三类 tabular dataset bucket、题型、budget 分维度），写入 `docs/reports/`。

## 运行方式

评测器：`tools/llm_eval/run.py`（独立脚本，不依赖主包）。

```bash
export OPENAI_API_BASE="https://api.gpt.ge/v1"
export OPENAI_API_KEY="<中转站 key>"
python tools/llm_eval/run.py <题目目录> --model <名> --temperature 0 --workers 8 --skip-existing
```

- 推理模型截断时调大 `--max-tokens`（默认 16384；runner 对 `finish_reason: length` 自动续写最多 3 次）。
- 凭证仅作环境变量，不落盘、不入 git。

## 成本估算

每题输入约 3k tokens；输出视模型推理长度约 1–8k tokens。按 gpt.ge 标价：

| 阶段 | 调用数 | 估算费用 |
|---|---|---|
| Stage 0 | 50 | 可忽略 |
| Stage 1 | 1500 | 约 $5–15 |
| Stage 2（约 10–15 模型；已测模型补 700 题） | 约 7,000–12,000 | 需按最终模型和输出 token 重新估算 |

## 风险与注意

- 中转站 model 名与官方可能不一致，Stage 0 先验证。
- 同一模型在不同阶段必须用相同参数（temperature=0），否则成绩不可比。
- 旧版 grok/Kimi 的失败提示：超长推理可能触发超时（客户端 timeout 120s），必要时单独降 workers。
