1 · 项目概览

ArchitectureIQ 是一个针对 toy 模型 的机器学习架构直觉 benchmark： 以很小的算力（MLP / 小型 transformer，10-seed GT ≈ 10–30s），测量大模型对 model / optimizer / loss / budget 配置空间的判断与研究能力。

论文定位（2026-08-02 起）：把 AutoResearch 拆解为 config 状态转移——一次研究过程 = 一系列 config → config 的转移（propose → 实验 → 观察 → 再 propose）。 本 benchmark 的原子单元 = 单次转移的质量，核心测的是「架构直觉」。

1.1 · Agent 职能与本次工作

我的职能覆盖 benchmark 全链路，是一个「设计—实现—执行—分析—文档」闭环：

  • 设计：把用户意图转化为可评测协议（工作树、预算规则、few-shot 策略、评分指标）。
  • 实现：按 spec→code→run→GT 不变量实现生成器、闭环 runner、题集与报告工具。
  • 执行：通过中转并发跑真实模型评测（eval key，reasoning_effort=high，无 token 上限），全程落盘思考过程。
  • 分析：聚合分数、定位模型行为问题（位置偏置、重复 propose、信息不足），区分「模型不行」与「题目不行」。
  • 文档：Plan、评测协议、pilot 报告、HTML 总览（本文档）。

本轮（2026-08-02 夜）完成：Plan 文档 → work-tree 生成器 → L1/L2 评测闭环 → 三模型 pilot → 发现并修复 5 个 bug（含 1 个数据完整性事故）→ 全量回归 1403 passed。

2 · 核心设计

2.1 · 核心不变量（Ground Truth 必须来自执行）

错误路径严禁：GT 用「并行逻辑重算」、prompt 展示的代码与 GT 执行代码不一致、 手写训练循环绕过生成代码。所有分数都必须来自执行 train.py 的 summary.json，prompt 展示的代码 = 执行的代码。

2.2 · 列式存储（backend/data）

列内容示例
problems/{problem_id}/数据集 spec + README + synthesize.py + 物化张量mvar_866b4e
trainers/{trainer_id}/family 训练脚本模板multivariate_regression_v1
candidates/{problem_id}/{candidate_id}.json闭合 config JSON（model/optimizer/loss/budget）c_969b50
results/{problem_id}/{candidate_id}/summary.json + curves.npz（10-seed GT）—

列式布局：一列拿全部题目 / 全部 configs / 全部曲线，各列体积可悬殊；generator 与存储解耦， 发布只带 data + eval。

2.3 · 工作树（work tree）

评测端视图 backend/eval/trees/{problem_id}/{tree_id}.json：一个好的 base + 若干 children（对 base 做 1–2 个 salient 编辑），每个节点都来自存量候选 + 已执行 GT， 因此「点亮」零算力；只有模型 propose 出真正的新 config 才跑新 GT。

节点状态：lit 已实验、loss 已知；unlit 待尝试。 few-shot 必须来自同一棵树（base + 2–3 个 lit 邻居带 loss），不引入树外随机 setting。

2.4 · 预算规则（用户要求，硬编码进建树与评分）

  • 模型参数量 ≤ base 的 1.1×；训练量（total_samples_seen）与 base 固定一致。
  • 违反预算的节点不进入工作树 → 树内每个节点都是合法 move；propose 越界直接拒绝并记错。

3 · 任务体系（L0 → L1 → L2）

层任务输入输出 / 评分状态
L0select_best（6 选 1，含 base） 5 个带 loss 参考 + 选项（不显示 loss） 选最低 loss 的 setting；正确率已有
L1plan_light（规划先点亮谁） 树视图：base + lit（带 loss）+ unlit（无 loss） light-first 命中率 + 完整排序 Spearman已实现
L2propose_loop（AutoResearch 闭环） 树视图 + 闭集约束 + K 轮上限 propose→GT→观察，K 轮内逼近最优；improve_base / oracle_gap / regret@k / wasted 率已实现

L2 每轮动作有两种合法选择：(a) 点亮 unlit 节点（propose 其精确 config，零算力揭示）； (b) 提出新 config（1–2 字段有意义编辑 → 跑真实实验）。重复 propose 已点亮节点 = wasted 轮次。 隐藏评分变体（不显示 lit loss）为规划中的对照实验。

4 · 实现架构

模块职责
backend/eval/worktree.py建树：base 质量门槛（排名 30%–65%）、1–2 salient 编辑、预算过滤、lit/unlit 视图、few-shot 选择
backend/eval/autoresearch.pyL2 闭环：propose→吸附闭集→存量深度相等匹配→新 GT（to_thread）→点亮→记录；批量共享 client+semaphore，完成即落盘

tests/test_autoresearch_eval.py6 个回归测试：树不变量、闭环评分、去重、base 不被覆盖
关键实现点：存量 candidate_id 的哈希来源与 short_hash(spec) 不一致 → 用规范后 config 深度相等匹配（忽略 candidate_id/problem_id/files 等派生键）实现「点亮存量零算力」； 新实验剥离派生键后重新哈希，绝不覆盖 base。

行为观察：模型第 1–2 轮倾向近邻小改（换 optimizer/loss），第 3–5 轮开始动架构 （depth/width/activation/layer_norm），多次出现「depth1 width128 + Adam」这类反直觉但有效的配置； 同时存在不少 wasted 轮次（重复 propose 已知 config）——这本身是「研究能力」的一部分，被 regret 曲线惩罚。

5.2 · 模型对比（同树 head-to-head）

同一批 6 棵树上 luna mean 42.8% vs terra 38.7%；deepseek-v4-flash 3/3 击败树内 oracle。 该评测能区分不同模型的研究/转移能力，且对便宜快速模型同样有效。

5.3 · L1 plan_light（95 棵树）

light-first 命中 50.5%（随机 ~18%）；完整排序 Spearman ≈ 0.01。 解读：模型能可靠挑出「最值得先点亮」的最优 unlit，但排不出紧区间的中间序 → 支持 「选项少、只问最优 / 二选一」的题型设计。

5.4 · L0 历史（修键后）

select_best_v2（6 选 1，随机 16.7%）：claude-opus-5 70% / terra 72% / luna 74%； two_choice：terra 66%、deepseek 52–54%（≈随机）、deepseek+强制推理 74%。 claude-opus-5 事后盲审结论：select_best 盲答 8% ≈ 随机 → 是信息不够，不是模型不行。
